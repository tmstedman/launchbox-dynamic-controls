# cfg cross-reference triage

Every `<Game>` in `assets/Defaults/Platforms/Arcade/Labels.xml` cross-checked against its MAME cfg in `romcontrols/cfg/{rom}.cfg`, following the same idea as `searchar`'s missing `P1_POSITIONAL` (a real, cfg-bound port with no Labels.xml entry at all -- not a `<Defaults>` fallback, not a whole-stick collapse covering it). "Bound" means at least one of a port's `standard`/`increment`/`decrement` sequences is a real joycode, not `NONE` -- searchar's own `P1_POSITIONAL` reads `NONE` on `standard` and only shows up on `increment`/`decrement`, which is why a check that only reads `standard` (or only reads `BUTTON*` ports) misses it.

This generalizes `audit_labels.py`'s existing "a button the config binds but nothing labels" check two ways: every `P1_*` port type, not just `BUTTON\d+`, and every sequence slot, not just the first one found. Note `audit_labels.py`'s own paths (`assets/Defaults/Controllers/`, `assets/Defaults/Labels/`) are stale since the Platforms/ restructure -- it won't currently run at all until pointed at `assets/Defaults/Platforms/{Platform}/`.

**1457** unlabeled-but-bound rows across **920** roms, split by how likely each is to be a real gap rather than a deliberate omission (`docs/label-import.md`'s own rules explain most of the noise: a hardware button wired but never read by the game, or a movement control the database never labelled, both left unlabelled on purpose):

- **High** (174) -- an exotic, single-purpose control (dial, pedal, paddle, positional, analogue stick axis, trackball, lightgun, ...). These are never "wired but unused" the way a 6th cabinet button can be, so a bound one with no label is very likely a real gap, same shape as searchar.
- **Medium** (62) -- a joystick direction (`P1_JOYSTICK*_UP/DOWN/LEFT/RIGHT`) bound in the cfg but covered by neither its own direction label nor the whole-stick label. `docs/label-import.md`'s own rule ("only label directions the config offers") makes this a named defect class -- though it can also mean the game's movement control was deliberately left out because the database never labelled it.
- **Low** (1221, not itemized below) -- a numbered face button (`P1_BUTTON`n`). Extremely common for real PCBs to wire buttons the specific game never reads; `docs/label-import.md` documents dropping these on purpose. Counts by port, for reference:
  - `P1_BUTTON3`: 505
  - `P1_BUTTON4`: 286
  - `P1_BUTTON2`: 214
  - `P1_BUTTON1`: 98
  - `P1_BUTTON5`: 36
  - `P1_BUTTON6`: 27
  - `P1_BUTTON7`: 17
  - `P2_BUTTON1`: 12
  - `P2_BUTTON2`: 10
  - `P1_BUTTON8`: 9
  - `P2_BUTTON3`: 4
  - `P2_BUTTON4`: 2
  - `P1_BUTTON9`: 1

Full detail for every row (including the low-confidence bucket) is in `cfg-cross-reference-full.csv` alongside this file.
