# Dynamic Controls

LaunchBox plugin that overlays controller button images and labels on the pause screen.

## Project layout

```
src/Core/          net6.0 — all business logic, no LaunchBox/WPF references
src/LaunchBox/     net6.0-windows — LaunchBox plugin host, WPF, Windows-only APIs
tests/Core.Tests/          unit tests (NSubstitute mocks, no disk I/O)
tests/Core.TestHelpers/    shared fixture builders used by both test projects
tests/Core.IntegrationTests/  subsystem + E2E tests against real fixture files
tests/LaunchBox.Tests/     LaunchBox-layer unit tests
```

`Core` must stay platform-neutral. Windows-specific APIs (registry, `SpecialFolder`, WPF) belong in `LaunchBox` or behind an interface implemented there.

## Conventions

**Three-layer type model** — data moves through three distinct shapes:
1. `*Config` / `*Node` / `*Entry` records — XML deserialisation targets. `Layout.xml` is the one config file that parses into a tree, so its DTOs take AST names (`*Node`, held by `LayoutDocument`); the flat settings files take `*Config`; name/value leaves take `*Entry` (see [conventions.md](docs/conventions.md#1-raw-config-dtos)); **all** properties are mutable `{ get; set; }` (the deserialiser needs setters — there is no `init` in this layer), collection fields are `List<T>` with `= []` initialisers (parsers call `.Add()` after construction); never escape the loader
2. Immutable positional records (`ResolvedLayout`, `ResolvedMapping`, `InputDefinition`, …) — built once, `IReadOnlyList`/`IReadOnlyDictionary` collections, `with` for derivation
3. Derived index fields (e.g. `CollapseInfo`) computed during the build and stored on the resolved record — not recomputed on demand

**Reference equality on `InputDefinition` keys**: dictionaries keyed by `InputDefinition` (e.g. `CollapseInfo`) use `ReferenceEqualityComparer.Instance`. Records have structural equality by default, so two distinct `InputDefinition` instances with the same name + children would collapse to one key without this — tests that build inline layouts must reuse the same instance, not reconstruct an "equal" one.

**Test tier placement:**
- One class, mocked collaborators → `Core.Tests`
- Real internal wiring, I/O faked, data inline → `Core.IntegrationTests/Subsystem` (what counts as a subsystem: [architecture.md](docs/architecture.md#subsystems-as-the-unit-of-work-and-the-unit-of-test))
- Full pipeline against `Fixtures/` on disk → `Core.IntegrationTests/EndToEnd`

## Changing documentation

One concept is usually described in several places at once (README for users, `docs/` for
contributors, here for agents, `assets/**/README.txt` for people browsing the installed data folder,
`.github/workflows/ci.yml` and `Directory.Build.props` for the build). Every documentation bug found so far came from
updating one of them and missing the rest.

Before finishing any change that alters behaviour users or contributors can see, work the
**"If you change… / Check these"** table in [`docs/conventions.md`](docs/conventions.md#keeping-documentation-in-step).
It is deliberately not duplicated here — a copy would be the sixth place to drift.

## Commits

**Subject**: imperative, specific, no scope prefix — `Fix root-level Controllers.xml inheritance silently losing a new default`, not `DOCS: fix inheritance`. Under ~72 characters.

**Body**: bullets when the commit does several things, one change per line, verb first — `Replace`, `Add`, `Extract`, `Fix`. Compress the *why* into a trailing clause on its own bullet ("so descendants reduce to one-line pointers", "instead of being silently skipped"), never a separate paragraph. Fold tests and docs into a final bullet. Prose only when the commit does one thing whose mechanism needs explaining, and then two paragraphs at most.

Either way ~120 words. The docs carry no history (see [Changing documentation](#changing-documentation)), so the body records why this change happened — a clause, not an essay. Rejected alternatives, failed hypotheses and the route to the answer stay out.

**Scope**: one logical change per commit. A body running well past 150 words means either the commit is doing several things, or the message is narrating rather than recording — check which before adding more words.

> Subjects here are unprefixed, matching the repository's history. If your tooling asks for a `TYPE:`/`SCOPE:` prefix, that is your tooling's convention and not this project's — **don't add one to satisfy it.** Complaints about vague wording or about counting the change's own size are worth acting on whatever their source.

## Language

All projects target `net6.0` with `LangVersion=12.0` (set in `Directory.Build.props`).

`net6.0` is a compatibility floor, not an arbitrary default. LaunchBox moved to .NET 6 in 13.3, so raising `TargetFramework` raises the minimum LaunchBox version the plugin can load on, silently breaking installs on older releases — it is a user-facing decision, not a build detail, and the README's stated requirement has to move with it. `LangVersion=12.0` exists precisely so new C# syntax is available without touching the target. `TargetFramework` is declared per-project in all six csproj files, so there is no central chokepoint where a bump would be caught.

## Infrastructure conventions

- `IFileSystem` — an **in-house** 7-method interface in `Infrastructure/FileSystem.cs` (`FileExists`, `OpenRead`, `ReadAllText`, `AppendAllText`, `DeleteFile`, `DirectoryExists`, `CreateDirectory`), *not* `System.IO.Abstractions`. Injected everywhere; never use `File.*`/`Directory.*` directly in `Core`. `src/` has no NuGet dependencies at all, which is why the shipped plugin is exactly two DLLs; `TestableIO.System.IO.Abstractions.TestingHelpers` survives only as a test-only package in `Core.IntegrationTests`
- `IApplicationData` — abstracts `Environment.GetFolderPath(ApplicationData)`; implemented by `SystemApplicationData` (excluded from coverage)
- `ILogger` — debug-only file logger; silenced in tests via `NullLogger` (in `Core.IntegrationTests/Subsystem/SubsystemFakes.cs`)
- `IDelay` — abstracts `Thread.Sleep`; implemented by `SystemDelay` (excluded from coverage). Exists so a bounded retry (e.g. `MameCfgLoader` waiting out a MAME cfg write) can be tested without actually sleeping
- `LayeredFileSystem` — wraps `IFileSystem` with two-tier path resolution (a real class, not an interface — the `IFileSystem` it wraps is the test seam). `Resolve(params segments)` returns `User\{segments}` if that file exists, else `Defaults\{segments}`, else null; loaders call it without knowing which layer wins, then read the result back through `FileExists`/`OpenRead` (rooted at the plugin root). `Defaults` / `User` expose each tier as a `RootedFileSystem` for the loaders that must check a specific layer (`InputLabelsLoader` merges both; `StaticImageResolver` reads `User` only). Components that take plain paths (logger, templates, RetroArch cfg from the emulator dir) get the raw `IFileSystem` injected instead. `Templates/`, `Logs/`, and the RetroArch emulator tree live at root and bypass layering.
  - Every loader resolves files this way, so a `User\` file *wholesale shadows* its `Defaults\` counterpart — **except `GlobalConfig.xml` and `Platforms\{Platform}\Labels.xml`**, which are merged. `ConfigLoader` merges the config field-by-field: it deserialises `Defaults\GlobalConfig.xml` as the base, then overwrites only the fields whose elements are *present* in `User\GlobalConfig.xml` (detected via an `XmlDocument` pass over the child element names). This stops a user file that sets one field from silently forcing every omitted bool back to `false`.
  - `InputLabelsLoader` merges the labels file *entry-by-entry*: it reads the `Defaults\` and `User\` copies separately (via `lfs.Defaults` / `lfs.User`, not `Resolve`) and lays the user's `<Game>` entries over the shipped ones (matched by `launchBoxId`, then `romName`), and the user's `<Defaults>` buttons over the shipped ones by name. One file now holds every game on a platform, so shadowing would make labelling one game drop the rest.
- `[ExcludeFromCodeCoverage]` — applied to infrastructure shims, factory classes, and pure DTOs

## Pipeline overview

```
StaticImageResolver.Find(game)     → early exit if Static/{platform}/{rom}.png/jpg exists
InputMappingService.Load(game)     → ResolvedMapping
InputLabelsService.Load(game, mapping) → ResolvedLabels
TemplateService.Load(templateName) → Template  (cached per name, never invalidated)
InputRenderingService.Render(...)  → RenderResult (flat lists of RenderedImage / RenderedLabel)
```

`ControllerOverlayService.Resolve` wraps the whole pipeline in a try/catch — any thrown exception is logged and converted to an empty `ControllerOverlayModel` so the pause screen doesn't show stale data. Tests against this service won't see exceptions surface; failures appear as empty output plus an error log entry.

## Input mapping

**Source priority** (first non-null wins): `PerGameXmlMappingSource` → `RetroArchMappingSource` → `PlatformDefaultMappingSource`. The first applicable transform (`MameInputMappingSource`) is applied on top of whichever source wins — transforms are first-match-wins like sources, not a chain. When a transform applies, `InputMappingService` re-splices the `Natural*` maps from the pre-transform baseline so remap detection still works correctly.

**Per-game overlay** (`PerGameXmlMappingSource`, via `MappingOverlay.Apply`): a `<GameMapping>` file overlays the selected controller's baseline. `<Mapping name="A" input="..."/>` replaces whatever that platform button had; `<Unmap name="C"/>` drops a baseline button with nothing in its place — for buttons a game isn't meant to use, in parity with RetroArch's `-1` sentinel. Baseline entries whose `name` appears in either list are dropped, then every overlay entry is appended — so repeating `<Mapping name="A">` with different `input` values drives several template slots from one platform button. The same `MappingOverlay.Apply` backs controller-level `inheritFrom` resolution.

**Whole-input derivation** (`WholeInputDeriver`, applied in `InputMappingService` after the naturals are spliced): a platform button naming a whole control (`JOYSTICK`, `Dpad-Any`) can't be moved by an emulator config, which binds directions individually. So after a transform, each whole-input button is re-evaluated against wherever its direction siblings ended up. The whole-and-parts pairing is discovered from `NaturalButtonToInput`, never parsed from names. Four rules: a whole is **claimed** only when *all four* of its directions are covered; a whole is **dropped** only when *every* direction has left it (a two-way joystick never drove four, so the weaker test would erase it); derived inputs are **appended**, so a directly-mapped button outranks one that merely reached the control, and a derived binding never displaces an existing `InputToButton` entry; and only emulator-derived layers are derived over — a per-game `ControllerOverrides` file can name a whole control itself, so its silence is taken as intent. Both MAME and RetroArch are covered, RetroArch since its swaps moved out of `RetroArchMappingSource` into `RetroArchSwapTransform`; note RetroArch remaps target digital buttons only, so they can strand a label but never move one onto a stick.

`ResolvedMapping` carries two parallel views:
- `ButtonToInput` / `InputToButton` — the *current* mapping (after per-game remaps/transforms)
- `NaturalButtonToInput` / `NaturalInputToButton` — snapshot of the mapping *before* transforms

**`IsMapped`** (used by `VisibilityEvaluator`): an input is considered mapped if a platform button currently drives it *or* if its natural physical button is still present in the current mapping. This keeps a button visible on screen after its action has been remapped away (e.g. ButtonB after MAME swaps BUTTON2 onto ButtonA — ButtonB's natural button still exists in the mapping).

`InputImageResolver` classifies each input as `Unmapped`, `MappedDefault`, or `Remapped`:
- **Unmapped** — no platform button drives this input; identity renders fall back to generic image, `useImage` renders get platform-specific variant
- **MappedDefault** — platform button drives this input and it's the same button as the controller default; image resolution prefers `{platformButton}.png` over the generic
- **Remapped** — a platform button drives this input but that button's *natural* target is a different input; image follows the physical button so the player sees what they're pressing

`AnalogToDigitalMirror` appends stick generics to every `ButtonToInput` list that contains a matching Dpad generic — it affects `ButtonToInput` only, not `InputToButton`, so image resolution is unaffected. The triggering attribute lives on `<Controller>` in Controllers.xml or on `<GameMapping>` in per-game ControllerOverrides.

## MAME plugin

Two parts with different roles:
- `MameControlsXmlSource` — `IInputLabelsLoader`; supplies labels from `controls.xml` when the emulator is MAME
- `MameInputMappingSource` — `IInputMappingTransform` (not `IInputMappingSource`); overlays JOYCODE overrides onto the baseline mapping rather than producing a full mapping from scratch

cfg lookup: `cfg/{romName}.cfg` first, fallback to `cfg/default.cfg`. MAME rewrites a game's cfg on every clean exit, so relaunching the same game soon after closing it can race that write — `MameCfgLoader` retries `FileExists` up to 3 times, 50ms apart, before treating the file as genuinely absent. JOYCODE values are translated to generic input names via `JoycodeMapping.xml` (must exist; empty mapping if absent). A single MAME port can list multiple JOYCODEs joined with `OR`, driving multiple generic inputs simultaneously — this is how joystick ports can label both Dpad and AxisLeftStick at once. A single JOYCODE can likewise map to more than one generic input in `JoycodeMapping.xml` itself — a bare analogue axis (`JOYCODE_1_XAXIS`) carries no sign, so both halves are declared against it rather than guessed; `JoycodeMappingLoader` accumulates same-joycode `<Mapping>` entries instead of the last one winning.

`MameCfgLoader` reads a port's `standard`, `increment`, and `decrement` `<newseq>` children, not just `standard` — a true analogue port (`DIAL`, `PADDLE`, `PEDAL`, `TRACKBALL_X/Y`, ...) can be driven by real analogue hardware (`standard`) or by two ordinary buttons nudging the value each way (`increment`/`decrement`) when no analogue device is bound. All three are translated and unioned (standard first, deduped) so a digital-only paddle/dial binding is recognized exactly like an analogue one; `NONE` means that sequence isn't bound and contributes nothing.

Arcade's platform button vocabulary (Controllers.xml `<Mapping name>`, Labels.xml `<Input name>`, controls.xml's own label names, per-game ControllerOverrides overlays) **is MAME's cfg port type, verbatim and without exception** — `P1_BUTTON1`, `START1`, `COIN1`, `SERVICE`. `MameCfgLoader` reads the `type` attribute straight into the mapping; there is no `NormalizePortType` any more, and `ControlsXmlLoader` likewise no longer strips a leading `P1_` from controls.xml label names.

The loader used to rewrite names on the way in: stripping `P1_`, dropping `P2_`, and collapsing `START1`/`COIN1` to bare `START`/`COIN`. Each rule was removed as it proved to cost real labels, the last one leaving a vocabulary that mirrored the cfg "except for two ports" — a rule nobody holds, so a port name read straight off a cfg silently failed to match. Renaming those two across every file (pre-1.0, so no migration path was offered) retired the method entirely.

Nothing is filtered by port *name* either. Reachability is decided one step later by the JOYCODE bound to the port, since `JoycodeMapping.xml` only ever declares `JOYCODE_1_*` tokens — another player's control translates to nothing and is dropped at the translation step. A name-based filter duplicated that check less accurately, because MAME routinely parks a player-1 control in a slot named for someone else, and that filter discarded exactly those. It cost `hwchamp`'s second boxing lever (`P2_AD_STICK_Z` on `JOYCODE_1_RZAXIS`), `20pacgal`'s Galaga start button (`START3` on `JOYCODE_1_BUTTON6`, alongside `START1` for Ms. Pac-Man), and the PlayChoice-10 cabinets' game-menu buttons (`SERVICE` on `JOYCODE_1_BUTTON5`) — each carved out separately as it was noticed, until the filter was dropped entirely. Keeping the raw name is also what lets a borrowed slot and a real `P1_*` slot coexist as distinct button names instead of one overwriting the other.

## RetroArch config resolution

Portable mode: `retroarch.cfg` exists next to `retroarch.exe` → config root = exe dir.
Non-portable: config root = `%APPDATA%\RetroArch`.
Cascade (later overrides earlier): `retroarch.cfg` (joypad driver only) → `config/{core}/{core}.cfg` → `config/{core}/{contentDir}.cfg` → `config/{core}/{rom}.cfg`.
Remap file: `config/remaps/{core}/{rom}.rmp`. Variant selection walks the full remap cascade (game → content-dir → core → common, first match wins); swap detection uses game-level only (see trust boundary below).
Variant selection: rmp wins over cfg; neither → platform Controllers.xml default.

**Trust boundary** — Controllers.xml is treated as already incorporating all non-game-specific configuration (global cfg, core cfg, core remap). Button swaps from those layers are not re-applied because resolving them requires knowing the physical controller layout via RetroArch autoconfig — too fragile to derive reliably. Which controller type is active (`input_libretro_device_p1`) is the exception: it is an explicit discrete choice with no hardware dependency, so it is read from the full cascade.

## Labels pipeline

1. `InputLabelsLoader` — the `<Game>` entry in `Platforms/{platform}/Labels.xml` (tried first). Lookup order: `launchBoxId` → case-insensitive `romName` → `RomNameUtils.NormalizeRomName` on both sides (strips `(...)`/`[...]` groups)
2. `MameControlsXmlSource` — `controls.xml` (only when `EmulatorPath` is MAME; gated on the emulator, *not* on `EnableMame`)
3. If no game labels found → the `<Defaults>` block of `Platforms/{platform}/Labels.xml` on its own
4. Entries are `<Input name="BUTTON1">label</Input>`; the `name` attribute is the platform button and the element text is the label, trimmed on read. A space-separated `name` is a button combination — an individual label is just a combination of one, and both resolve the same way: a generic's label comes from whichever entry names *exactly* the buttons that drive it, no more and no fewer. A label naming a subset (e.g. one button of a shared trigger three buttons all fire together on) is not a partial match, it simply isn't that generic's label — so when three buttons share a trigger and each pair also shares its own distinct one alongside it, only the entry naming all three can ever label the fully-shared generic; a 2-button entry only ever labels the generic that pair alone reaches
5. When no entry names the full set of buttons reaching a generic, that set is retried once with any button dropped whose reach there is weaker than its strongest (lowest-rank) claim — a button's own bindings precede any `analogToDigital` mirror in its list, so this lets a mirrored claim step aside for the real binding underneath it. If neither the full set nor that narrower one matches and more than one button remains, it logs at `Error` and leaves the input unlabelled — none of those buttons' own text was written to describe a generic several of them drive at once, so no single label there is true
6. Every `<Defaults>` entry is inheritable — merged into game-specific labels for any platform button the game didn't name (e.g. Start=Pause applies even when the game only defines button labels). There is no `inherit` attribute
7. Clone-of ROMs inherit their parent's labels
8. `InputLabelsService.CollapseWholeDirections` reconciles a whole-control generic (`ButtonDpad`, `AxisLeftStick`, `AxisRightStick`, per `WholeInputs.PartsOf`) against its four individual directions, in both directions: if the whole has a label but none of the four directions have any label/mapping of their own (a direct whole-only reach, e.g. N64's `Dpad-Any`), the whole's text is copied onto all four so every direction renders identically bright; if 2, 3, or 4 directions already agree on identical text and the rest are genuinely blank (never labelled, not merely different), that shared text is copied onto the whole's own key. Individual per-direction entries are never removed, only ever added to — this is what lets the layout tell "the whole collapsed" apart from "all four individually disagree" (see `<Condition>` below)

## Layout rendering notes

- `showIf="auto"` → `HasLabel` when game-specific, `IsMapped` when default. This serves two distinct rendering modes: for Arcade/MAME games where `MameControlsXmlSource` supplies labels, `IsGameSpecific=true` so `auto` resolves to `HasLabel` — controls.xml acts as a button mask. For platforms with custom images but no per-game labels (e.g. Sega Genesis default), `IsGameSpecific=false` so `auto` resolves to `IsMapped` — all mapped buttons are active.
- `VisibilityEvaluator.GetVisibilityFlags` folds a whole control's four direction names into its own `HasLabel`/`IsMapped` check — what makes `ButtonDpad`'s own glyph light up under `auto-blur` when any direction has a label, even though the whole itself never does. It looks these names up directly from `WholeInputs.PartsOf` by the Input's own `Name`, not from `Children` nesting — the direction Inputs are siblings of their whole in Layout.xml, not its structural children, so fan-out is a fact about names, independent of tree shape. An Input whose name isn't a whole gets an empty list. Since the lookup is by name and static, there's no per-template index to precompute or cache — no `InputDescendants` on `ResolvedLayout` any more.
- `showIf="label"` → `HasLabel` always; `showIf="mapping"` → `IsMapped` always
- `Container` (formerly `<Group>`) is the positioned cluster type — `<Group>` used to be split into a plain conditional wrapper and a separately-named `<Stack>` for positioning; the two were merged (Stack renamed to Group) since every real usage paired them 1:1. That's since been un-merged the other way: `Container` keeps the positioning half but drops the implicit conditional half entirely — it resolves to `Container` (the record), and is **always** rendered once `LayoutFilter` reaches it. It never decides its own visibility any more; wrap it in an explicit `<Condition>` when gating is wanted (see below) — a `<Condition>` was already the right tool for "all four individually agree" vs. "some subset", and now it's the *only* tool, so a Container's own inclusion is always a stated fact in the template, never derived. Its own members still handle their own individual visibility via `showIf` once the Container itself is reached. `vAlign` (`top` default / `bottom` / `center`) picks which slot the declared `y` refers to, by shifting the container's origin up by its fixed slot count before slots are laid out — resolved once at template-load time from the nominal (uncollapsed) slot count. Combined with `collapse`, a vacated slot would otherwise drift the anchor toward `top`, so `LayoutFilter` corrects for it at render time: it re-derives `StackVAlign.Shift` against however many slots are actually left and folds the difference uniformly into every member's offset, on top of collapse's own per-vacancy shift — keeping `bottom`/`center` pinned to `y` regardless of how many slots collapse away. The vAlign string is validated (logged, defaulted to `top`) exactly once, in `LayoutResolver`; `CollapseInfo.VAlign` carries the already-normalized value so the render-time correction never re-validates it. A nested `<Container>` is never transparent — even with no `x`/`y`/`gap` of its own it always establishes its own frame and occupies one opaque slot as a block in its parent (a `CollapseGroupBuilder` concern, tracked via `Container`'s reference identity, not a field)
- The style cascade (`style`/`showIf`/`minOpacity`/`inactiveBlurRadius`/`fontSize`) is one mechanism (`LayoutResolver.ResolveStyle`, producing a `ComputedStyle`) shared by every element that carries these attributes, not four ad-hoc `Inherited*` fields threaded separately. `IStyledNode` (`Style`/`ShowIf`/`MinOpacity`/`InactiveBlurRadius`/`FontSize`) is implemented only by `InputNode`/`ContainerNode` — the two types ever treated polymorphically as a cascade *origin* whose result flows to descendants via `BuildContext.Style`; `OverlayNode`/`LabelNode` are leaves reached only through their own concretely-typed Build method, so they call `ResolveStyle` directly with their own fields instead of implementing the interface — avoiding giving `Overlay` a `FontSize` member or `Label` a `MinOpacity`/`InactiveBlurRadius` member neither could ever populate. `BuildContainer` resolves with `cascadeAmbient: false` — the one asymmetry: an *empty* `<Container>` (nothing of its own for `showIf`/`minOpacity`/`inactiveBlurRadius`) does not relay a wrapping Input's own ambient value through to members, only its *own* explicit value if it sets one. Without this, a Container nested inside a styled Input (e.g. `AxisLeftStick`'s `auto-blur`, `minOpacity="0.3"`) would leak that value four levels down into a `small-label-vacate` direction, turning its vacate-to-zero into a fade — the real regression this guards against. `FontSize` always keeps cascading through an empty Container regardless (it has a template-wide default baked into the root context to reach); `BuildInputDefinition` always cascades fully (default `cascadeAmbient: true`), so a nested `<Input>` that sets nothing of its own now genuinely inherits from its structural parent, the same as a Label/Overlay always has — a deliberate consistency expansion from the historical "child inputs start fresh" rule, covered by `LayoutResolverTests`' nested-Input-inheritance cases.
- `OneOf` picks first alternative where `AnyVisible` is true. Since a `Container` never decides its own visibility, `AnyVisible` has no case for it at all (falls to the same default as any unhandled type) — a `Container` can only ever be a `OneOf` alternative when wrapped in a `<Condition>`; a bare one would make that alternative permanently unselectable. All 8 `Container`s in the shipped template are either top-level (never asked `AnyVisible` at all) or `<Condition>`-wrapped, several of those `Condition`s existing *specifically* to replace the implicit check a `<Group>` used to supply for free — see the directional-inputs bullet below
- `Condition` (`all`/`any`/`none` over named generic inputs' label/mapping state) gates its children on those names directly, by dictionary lookup — it never folds in its own children's structural descendants (unlike the old `<Group>`'s implicit any-descendant-visible check, which no longer exists at all). This is what lets it gate a subtree on a name that isn't (or isn't only) one of that subtree's own inputs. A compound AND is expressed by nesting one `Condition` inside another; transparent to coordinates and slot counting — unlike a nested `Container`, which never is. `match` supports `label`/`mapping`/`auto` (mirroring `ShowIfCondition`'s three modes exactly, including `auto`'s `isGameSpecific ? HasLabel : IsMapped`) — `auto` was missing for a while (silently defaulting to `label` with a logged error) despite `AxisTriggerLeft`/`ButtonLeftShoulder`'s wrapping `Condition` already being authored with `match="auto"`, which stranded that whole pair for any ROM with zero labels at all (not just missing a game-specific file, no platform defaults either) even when one of them was genuinely mapped
- A bare `<Label>` (no `<Input>` of its own) can sit inside `<Container>`/`<OneOf>`/`<Condition>`, most usefully the latter — it attaches to whichever `<Input>` is ambient at that point in the tree (`LayoutResolver.BuildContext.CurrentInputName` at template-load time for identity/origin/style inheritance; `LayoutFilter`'s own walk rediscovers the same owning `InputDefinition` at render time, since it doesn't exist as an object yet while its own children — this one included — are being built). Reset on entering a nested `<Input>`, unaffected by passing through `Container`/`OneOf`/`Condition`. Merged into `LayoutInput.Labels` once, by `LayoutFilter`, alongside that Input's own static `Labels` — so `InputLabelRenderer` never needs to know two sources existed. A wrapping `Condition` decides only whether it exists at all this game, never its own opacity, which its own `showIf` still governs. No enclosing `Input` at all (ambient or direct) is a template-authoring error, logged once at load time — **unless** a `<Container for="Name">` supplies the ambient Input explicitly (see the directional-inputs bullet below): `ContainerNode.For`/resolved `Container.ForInputName` carry the name through to both build time (`CurrentInputName`, for style/origin) and render time (`LayoutFilter` resolves it against the template's own top-level Inputs, once per `Filter()` call, since it can't be baked in at resolve time as an object reference the way structural nesting could). Deliberately not on `OneOf`/`Condition` — those are pure control-flow (alternative selection, named-input checks), unrelated to identity, and `Container` already carries the rest of an Input's structural attributes (`x`/`y`/`gap`/`style`), so `for=` fits the same place. There is no equivalent bare `<Render>` — an Input's own image is described directly by attributes on `<Input>` itself (`width`/`height`/`useImage`, alongside `showIf`/`minOpacity`/`inactiveBlurRadius`), not a separate child element, so it can never appear loose
- A loose `<Label>` placed directly in a `<Container>` (or reached through `OneOf`/`Condition` nested in it) centers on the visual midpoint of however many of that Container's slots actually survive **for the current game** — not baked once at template-load time, since which slots survive `collapse="true"` is a per-game fact `LayoutResolver` has no way to know. `Container` carries its own static shape (`DeclaredOriginY`/`Gap`/`VAlign`/`Collapse`) as plain fields — deliberately not sharing the per-Input `CollapseInfo` instance member Inputs are keyed by, so each type stays a single self-contained concept (see `Container`'s doc comment for the encapsulation tradeoff considered and rejected). `LayoutFilter.CollectVisibleElement` tracks `currentContainer` the same way it tracks `currentInput` — reset on a nested `Input`, overwritten (never transparent) by a nested `Container`, passed through unchanged by `OneOf`/`Condition` — and `LayoutFilter.ResolveLooseLabel` computes the actual center from it, once `inputsToRender` is complete, reusing `CollapseGroupBuilder.Flatten` and the same per-slot hidden-check `ComputeCollapseAdjustments` uses for member Inputs' own Y offsets. Without `collapse="true"` the container's full nominal slot count is always used, so nothing varies by game in that case. A container member's own direct `<Label>` is unaffected either way, since `inputCtx` never carries any of this
- Face-button cluster is a `<Container style="input-label">` (showIf=label, hoisted off the four member `<Input>`s since none of them override it) of `<Input>`s — each button owns its own `Line_ButtonX.png` individually, not a shared Container-level overlay, so unlike the seven `_Multi.png`/meta-buttons clusters below there's no overlay to move out first — wrapped in `<Condition any="ButtonY ButtonB ButtonA ButtonX" match="label">`. Since a Container never decides its own visibility, that explicit `Condition` is what makes the whole cluster disappear entirely when no face button has a label — without it, the members would individually fade to the template default instead, a real visual regression an earlier session caught via the E2E suite (the meta-buttons cluster, `ButtonStart`/`ButtonBack`, is wrapped the same way and for the same reason)
- The meta-buttons cluster and the six `_Multi.png` alternatives (AxisLeftStick/AxisRightStick/ButtonDpad, both the "2-3 agree" and all-distinct-fallback alternative of each) *do* carry one shared overlay for the whole cluster — and in every one of those, the overlay sits as a `<Condition>` sibling of the `<Container>`, not a child of it, precisely so it's outside the Container's style cascade: the repeated `style="small-label-vacate"` (or `small-label-blur`) on every member Input now lives once on the `<Container>` instead, and moving the overlay out is what keeps that hoist from also handing the overlay a `showIf`/`inactiveBlurRadius` it never had. The three "2-3 agree" alternatives additionally pin `fontSize="24"` explicitly on their loose, centered `<Label>` — the Container's own resolved `fontSize` is now 22 (from the hoisted style), but the merged label rendered at the template's root default (24) before this existed and that's deliberately preserved, not "fixed," since nothing pinned it as a test before. `for="AxisLeftStick"`/`for="AxisRightStick"`/`for="ButtonDpad"` still only affects the ambient owner *inside* the `<Container>` — the sibling `<Overlay>` outside it is genuinely ownerless (see the loose-`<Overlay>` bullet below), which happens to be moot here since none of these seven set an explicit `showIf` anyway
- Directional inputs (`ButtonDpad`, `AxisLeftStick`, `AxisRightStick`) use a `<OneOf>` gated by `<Condition>` rather than plain any-descendant-visible alternatives, so a merged label can render without repeating text next to every agreeing direction. The `<OneOf>` is a **sibling** of its whole's own bare `<Input>` (`<Input name="AxisLeftStick" style="auto-blur" .../>` self-closing, then a plain `<OneOf>` immediately after) rather than nested inside it — nesting used to be the only way to get the `showIf="auto"` fan-out above, but that's now sourced from `WholeInputs.PartsOf` by name regardless of tree shape, so the one thing nesting still bought here (positioning, and the loose-label anchor) turned out to not need it either: each direction's own `<Container>` carries its own absolute `x`/`y`, so it never relied on the whole's coordinate origin, and `for=` on the one `<Container>` that carries a loose `<Label>` (the "2-3 directions agree" alternative) replaces the ambient-Input anchor nesting used to supply for free — the "all agree" alternative's label sits on a real `<Input>` and the fallback alternative's labels are each direct Input children, so neither of those needs it:
  - `AxisLeftStick`/`AxisRightStick` only, first alternative — single glyph (`Line_AxisLeftStick.png` etc.), gated by a *nested* `<Condition any="{Whole}" match="label"><Condition all="{all 4 direction names}" match="label">`: the outer confirms the whole actually collapsed to one shared label, the inner confirms all four directions individually carry it. Both are required — an all-four-*disagree* template also leaves every direction individually labelled, so the inner check alone can't tell the two apart
  - Merged alternative (all three controls) — `<Condition any="{Whole}" match="label">` wrapping a loose `Line_..._Multi.png` `<Overlay>` (a sibling of the `<Container>` below it, not its child — see the loose-`<Overlay>` bullet above) and a `<Container style="small-label-vacate">` that carries the per-direction mini-icon `<Input>`s (each with its own image but no `<Label>`, so a genuinely-blank direction dims independently while present ones render at full brightness) and one shared `<Label fontSize="24">` loose inside the Container, centering against its declared `vAlign="center"` position with no hand-tuned offset. Fires whenever 2, 3, or 4 directions agree (`CollapseWholeDirections` above put the shared text on `{Whole}`'s own key either way)
  - Final alternative — the all-distinct fallback: every direction renders its own icon and its own label, each Input now inheriting `style="small-label-vacate"` from the `<Container>` rather than repeating it. Also wrapped in `<Condition any="{all 4 direction names}" match="label">` now — a bare `Container` can never be a `OneOf` alternative (see the `OneOf` bullet above), so without this the `OneOf` would have no way to select this alternative at all when it's the one that should fire
- An `<Overlay>`'s `InputName` comes from its parent: null when parented to a `<Container>`, the input's name when parented to an `<Input>`. A bare `<Overlay>` (no `<Input>`/`<Container>` of its own) can sit anywhere a `<Label>` can — inside `<Container>`/`<OneOf>`/`<Condition>`, or directly in `<Body>` — resolved by `LayoutFilter` the same way: an ambient `<Input>` wins first (joins that Input's own `Overlays`, merged into `LayoutInput.Overlays` alongside `Labels`), else an ambient `<Container>` (joins its `Overlays`, folded into the same aggregate-flagged group-overlay emission its own direct children already get — collected during the same recursive walk that visits everything inside it, so by the time a `Container` emits its overlays every loose one in its subtree has necessarily already been found), else neither at all. Unlike a loose `<Label>`, a fully ownerless `<Overlay>` is not a template-authoring error — position never depended on an owner to begin with (it resolves against whatever origin is ambient, same as always), and there's simply no fold-in target for visibility, so it renders unconditionally as its own template-level overlay (its own `showIf` still governs its own opacity — only `showIf="always"`, the default, ever actually shows something with no flags to check). `OverlayNode`/`OverlayElement` carry this the same way `LabelNode`/`LabelElement` do, including the `ParseContainerNode` ordering fix that keeps a Container's own *direct*-child `<Overlay>` landing on its dedicated `Overlays` list rather than being swallowed by the generic loose-child path
